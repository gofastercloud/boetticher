# Client certificates

The installation creates a private Root CA and Issuing CA. CA private keys stay in encrypted SOPS material. Server private keys for the monitor and portal are generated on their endpoints, remain there, and are never copied into the controller repository or portal. The controller receives only endpoint CSRs, validates their approved SANs, and returns signed certificate chains. Certificate metadata and fingerprints may be committed as generated evidence.

Client private keys are generated by the controller and stored under the
external runtime directory, not in Git. Treat exported client bundles as
private credentials.

Use one shared `operator` identity for operator devices when a common Pulse and
future-portal role is appropriate:

```sh
boetticher pki client create operator --site my-boetticher
boetticher pki client export operator --site my-boetticher --output operator.pem
```

The kiosk receives a separate non-operator identity:

```sh
boetticher pki client create lab-display-01-kiosk --site my-boetticher
boetticher pki client export lab-display-01-kiosk --site my-boetticher --output lab-display-01-kiosk.pem
```

```sh
boetticher pki trust export --site my-boetticher --output boetticher-ca.pem
```

Pulse maps the exact `operator` certificate subject to the operator account and
the exact kiosk subject to a non-administrative kiosk account. The proxy never
forwards an arbitrary certificate subject as an application identity. Sharing
the operator private key across Mac, iPhone, and iPad is convenient but makes
revocation collective; revoke and reissue the operator identity if any one of
those devices is lost or compromised. The kiosk identity remains independently
revocable.

The export command refuses private-key output to stdout. Revocation records identify the exact certificate serial, and the next deployment generates and distributes a signed CRL to the mTLS endpoints. Until that deployment and its endpoint reload complete, treat the certificate as still active.
